Claude.AI（Fable）より。2026-11-16。Claude Code の依頼（`2026-11-16_ClaudeCode_タイプ1企画の依頼_ClaudeAI宛て.md`）の1番への返事。
土台：同日のユーザーとの相談と、`2026-11-16_ClaudeAI_タイプ2・3の総合チェック.md`。決定ではありません。（ユーザー）と付けた所だけがユーザーの考えで、ほかは私の案です。

## 1. タイプ1とは

- 3種の言い方（ユーザー、11-16）：1 プログラムの賢い対応／2 HP情報と設定でフリートークを重視するAIセッション／3 HP情報と設定に、トークの誘導を加えたAIセッション。
- 三つの違いは、賢さの出どころです。1はデータと決まり、2は客の言葉を追うAI、3は店の道筋へ導くAI。
- タイプ1は「2・3からAIを抜いたもの」ではありません。2・3の①〜③（ロケーション確認）はすでにAIなしで動いていて、それを④から先まで伸ばしたものがタイプ1です。
- 契約：店は何も契約しません。Claude API も要りません（売り切り）。設定のときのHP読み取りも、API を使いません（ユーザー）。
- 11-04 の線はそのまま守ります。客の画面で即座に反応し、最後は問い合わせで終わる。後で店が答える形（選択の多い問い合わせフォーム）にはしない。

**フォームに落ちないための検査項目を一つ置きます。「選ぶたびに、客が知らなかったことが一つ返る」。** 設計も初期値も、これで確かめます。

## 2. 流れ

| 段 | 中身 | 誰が持つか |
|---|---|---|
| ⓪ | 地図・ピン | 共通（今のまま） |
| ①〜③ | ロケーション確認：設問と公開データの表（ユーザーの呼び方） | 共通（今のまま） |
| 分け | ①〜③の結果から、カテゴリーが決まる | アプリ |
| ④ | カテゴリー別の選択肢。**ここを通ることが企画の最大の山**（ユーザー） | アプリ（初期設定）。どの一式を使うかは「重視する業務内容」で決まる（7章） |
| ⑤〜 | 選択 → 返事 → さらに選択。＋ボタンで段を足せる（ユーザー） | 店 |
| 終点 | 問い合わせ。通った道とデータシートを添える | 共通 |

①〜③までは共通で、最後の選択からニーズ把握へ分かれる所がタイプ1の企画点です（ユーザー）。

**趣旨（ユーザー、11-16）：** 基本情報と最初の選択までは、必ずしてもらう。そこが最大の山で、通れば問い合わせる気になりやすい。その先の選択は「聞かれて、言いたいこと」を重ねていく。店と客を結びつけるのが、このボット企画の狙い。

## 3. カテゴリーと条件札（アプリが持つ分け方）

分け方を店に作らせると入口でつまずくので、アプリが持ちます（ユーザーと合意）。

**カテゴリー＝幹。** 設問の最後「いまの使われ方」で分けます。

| | カテゴリー | 客の状況の読み |
|---|---|---|
| K1 | 住んでいる家がある | 今すぐではない。将来の渡し方、住み替え |
| K2 | 空き家・古い家がある | 持て余している。解体・貸す・売る |
| K3 | 何もない（更地） | 何に使うか。建てる・貸す・売る |
| K4 | 駐車場・畑など | 今の使い方を続けるか、変えるか |

**条件札＝枝の絞り込み。** 道・形の答えと公開データから、アプリが付けます。

| 条件札 | 元 |
|---|---|
| 建て直しに難あり | 通路が2mない |
| 道側へ下がる | 前の道が狭い |
| 角地 | 2つの道に面している |
| 段差あり／形がいびつ／車を置きにくい／境目が未確定 | 設問B |
| 分からない所あり | 「わからない」「測ったことがない」 |
| 住居系／商業系／工業系 | 用途地域 |
| 駅が近い／遠い | 周りのデータ（駅までの距離） |
| 弊社の扱う地区 | ピンの地区 × HPから数えた「扱う地区と物件」 |

カテゴリーは選択肢の顔ぶれを決め、条件札は選択肢を絞り、文を足します。

## 4. 選択肢に価値を出す（企画の中心）

タイプ3では、土地に合わないボタンをAIが言葉で補います。タイプ1には補い手がいないので、選択肢そのものに判断を載せます。方法は四つです。

**4-1　出せない選択肢は、理由つきで薄く出す。**
消すのではなく、理由を見せます。客は選ぶ前に一つ知ります。
> ［建て直す］ 通路が2mないため、今のままでは難しい → ［お隣と合わせる］を見る

**4-2　選択肢に数字を載せる。**
プログラムが計算した値を、ボタンの下に一行で添えます。計算はプログラムなので、計算ミスで疑われる心配と両立します。
> ［売る］ 国の標準地の値で単純に計算すると、約1,850万円が目安
> ［建てて貸す］ 容積率200％なので、延べ約240㎡まで
> ［郊外の広い土地へ移る］ 同じ額で、◯◯町のあたり（北東12km）なら約95坪

**4-3　先頭の一つに印を付ける。**
条件札から「この土地なら、まずこれ」を一つ決め、先頭に置きます。「間違ってよい、だから逃げない」の、タイプ1での形です。印の決まりはアプリの初期値で、店が外せます。

**4-4　選んだ後の返事は、三つの部品を重ねる。**

| 部品 | 中身 | 誰が持つか |
|---|---|---|
| 受け | その選択肢への店の一言 | 業務内容ごとの初期設定で入る（7章）。⑤から先は店が書ける |
| 土地の一文 | 条件札ごとの事実（今の `survey.js` の facts と同じ形） | アプリの初期値。店が直せる |
| 数字 | データの穴に値を入れた一文 | 文は店、値はプログラム |

最後に、次の選択への問いを一つ付けます。

## 5. 文の持ち方 ― 膨らみを止める

4択を3回重ねると、道筋は64通りです。道筋ごとに文を書かせると、設定は成り立ちません。

- **文は選択肢ごとに持ち、重ねて返す。** 4択3回なら、書くのは12です。
- **組み合わせで言うことが変わる所だけ、特例を足す。** 「この選択肢 × この条件札のとき、文を差し替える」。店は例外だけ書きます。
- **埋めていない枝は、そこで問い合わせへ行く。** どの道も終点は問い合わせなので、浅くても壊れません。店は浅く始めて、得意な所だけ深くできます。枝の深さが、店の得意の形になります。

**データの穴**（文に差し込める値。今の部品で出せるもの）

| 穴 | 元 |
|---|---|
| 地域名、面積 | ピン・入力 |
| 用途地域、建ぺい率、容積率、建てられる延べ床の上限（面積×容積率） | 国の公開データ |
| 標準地の単価、単純計算の目安、足し引きの内訳と目安額 | 標準地（`3_ai_main.html:443`、`altland.js`） |
| 最寄り駅と距離、学区 | 周りのデータ（`around.js`） |
| 代替え地の例（地域名・方角・距離・広さ） | `altland.js` |
| 弊社の扱う地区・物件の種類 | HPの物件ページ（`shop/listings.js`） |

値が取れないときは、その穴を含む一文だけを落とします。「現地で確認します」には差し替えません。総合チェック3章の線（プログラムが持っているデータは言い切る。客が知らないことだけ、確かめる理由にする）をそのまま使います。

## 6. 管理画面 ― タイプ1こそ重要（ユーザー）

タイプ1では、店が書いた文がそのまま客の画面に出ます。管理画面に書いたものが商品です。構造はタイプ2・3と違い、フローチャート式です（ユーザー）。

**見え方は二つ。**

1. **なぞって設定する画面（主）。** 客と同じようにボタンを押して進み、その場で、初期設定の文を確かめ、⑤から先の選択肢と文を足します。＋ボタンは「今いるこの場所の次」に段を足します。11-04 の「管理画面は客の画面と同じ番号で」の延長です。
2. **全体図（地図）。** カテゴリー4列 × 段。どの枝が埋まり、どこが問い合わせで終わるかを見ます。直す場所へ飛ぶための図で、ここでは編集しません。

**設定を軽くする仕掛け。**

- **最初の形はアプリが入れる。** 入口はHPのURLと「重視する業務内容」（7章）。業務内容のチェックが決まると、カテゴリーごとの選択肢と文の初期値が入ります。タイプ3のボタン文言の初期値を元にできます。店は「なるほど」と同調できれば、そのまま使えます（ユーザー）。
- **試しの土地。** 見本の土地（角地の更地／通路の狭い空き家／駅前の駐車場 など）を切り替えて、絞り込みと文を確かめます。
- **穴は一覧から差し込む。** 記号を覚えさせません。差し込むと、試しの土地の値で見えます。
- **店が変えられる範囲。** 次の章のとおり、初期設定を土台にし、店は「重視する業務内容」のチェックと順番を変えることで一式を入れ替えます。

## 7. HP読み取りと「重視する業務内容」 ― この企画の結論（ユーザー、11-16）

（経緯：私は先に「HPに頼らない型」、次に「AIを1回使う当てはめ」と書き、どちらも違いました。この章はユーザーの説明で書き直したものです。）

### 7-1　決まり（ユーザー）

- 心配は、店が選択肢を変えて独り相撲になること。基本は、初期設定に店が「なるほど」と同調すればよく、足すのは店のニーズ程度。
- HP読み取りが、デフォルト選択肢の発動キーになる。
- API は使わない。プログラムの判断で、HPからこの会社のニーズを拾う。
- HPの読み取りでデフォルトが一旦入る。その次に「重視する業務内容」の選択を置き、選ぶと選択肢の初期設定が入れ替わる。
- この操作で、設定の意味と機能の意味が店に分かる。
- 「重視する業務内容」は、対応できるなら複数選択にしたい。

### 7-2　管理画面の流れ

| 順 | 店がすること | 画面で起きること |
|---|---|---|
| 1 | HPのURLを入れる | プログラムがHPを読み、業務内容を判定する。その業務内容のデフォルト選択肢が入る |
| 2 | 「重視する業務内容」を見る | 判定された業務内容に、点の高い順でチェックが入った状態で出る。根拠が横に出る |
| 3 | 同調するか、チェックと順番を変える | 変えるたびに、選択肢の初期設定が入れ替わる |
| 4 | （望めば）店のニーズを足す | ⑤から先の段を＋で足す |

店は文を一つも書かずに、3で終えられます。

### 7-3　複数選択の組み立て（私の案）

複数にしても混ざらないように、決まりを四つ置きます。

1. **順番を持つ。** チェックした業務内容に1番・2番…と順を付けます。初期値はHPの判定の点の高い順で、店が並べ替えられます。
2. **選択肢はアプリの中で一つずつ名前（番号）を持つ。** 「売る」は、どの業務内容から来ても同じ「売る」です。重なった選択肢は一つにまとめ、返す文（受け）は順番が上の業務内容のものを使います。
3. **④に出すのは5個まで。** 1番の業務内容の選択肢から埋め、空きに2番、3番の分を足します。入りきらない分は［ほかのご相談］の先に出します。先頭の印（4-3）は1番から決めます。
4. **土地の絞り込みは、そのあとに掛ける。** 業務内容で顔ぶれが決まり、カテゴリーと条件札（3章）で、その土地に出すものが絞られます。

5章の「文は選択肢ごとに持つ」があるので、業務内容をいくつ選んでも、店が書く量は増えません。

### 7-4　入れ替えを、その場で見せる（私の案）

「操作で意味が分かる」ためには、変わる前と後が同じ画面で見えることが要ります。

- 「重視する業務内容」のすぐ横に、客の画面の見本を置きます。試しの土地（例：空き家のある角地）は固定したままにします。
- 見本の選択肢には、どの業務内容から来たかの札を小さく付けます（管理画面の見本だけ。客の画面には出しません）。
- チェックを入れると、その業務内容の札が付いた選択肢が足されます。外すと消えます。順番を変えると、並びと先頭の印が変わります。
- 土地を変えずに店の側だけ変えるので、「選択肢は、客の土地と店の重視が重なって決まる」が、説明なしで伝わります。

複数選択は、入れ替えが見えにくくなると私は心配しましたが、札を付ければ「この業務内容が、この選択肢を連れてくる」が一つずつ見えます。一つだけ選ぶ形より、意味が伝わりやすいと考え直しました。零細の店は実際にいくつもの業務を兼ねているので、HPの判定も一つに絞るより当たりやすくなります。

### 7-5　三つの層

| 層 | 決め手 | 誰が決めるか |
|---|---|---|
| 重視する業務内容（複数・順番つき） | 店の側。どの初期設定の一式を、どの順で使うか | HPの判定が初期値、店がチェックと順番を変えられる |
| カテゴリー | 客の土地の使われ方（3章） | アプリ |
| 条件札 | 客の土地の様子と公開データ（3章） | アプリ |

業務内容の枠は、11-04 の業態モード4＋1（仲介情報屋／開発優先／アドバイス優先／相続・税／空）を元にします。「うちはこの中にない」と言わせない範囲、という当時の狙いがそのまま生きます。

### 7-6　プログラムの判定（API なし）

材料は、今の `shop/read.js`・`shop/listings.js` がAIなしで拾っているものです。

| 材料 | 例 |
|---|---|
| 専用のページがあるか | 売却サポート、買取、相続、空き家、管理、土地活用 |
| メニュー・リンクの名前 | 売りたい、買いたい、貸したい、相続のご相談 |
| 売買の物件の出方 | 地区 × 種類、件数の偏り（土地が多い、収益物件が多い など） |
| 免許番号 | 更新回数 |

- **言葉より構造を重く読みます。** 本文の言葉を数えると、宣伝文句で誤ります（どの店も「相続もお任せください」と書きます）。専用のページ ＞ メニューの名前 ＞ 物件の出方 ＞ 本文の言葉、の順に重みを付けます。
- 形は、客の言葉の察知（`server/trigger.js`）と同じにします。業務内容ごとに点を付け、線を越えたものすべてに、点の高い順でチェックを入れます。線の少し下のものは、チェックなしで「HPに少し記載があります」と添えます。
- **根拠を見せます。** 「売却サポートのページと、売買の土地12件から『仲介』と読みました」。
- **何も読めない店**は、総合（アドバイス優先）だけにチェックを入れます。
- **確かめ方。** 11-16 の10社には、AIが読んだ結果が記録に残っています。それを答え合わせに使い、プログラムの判定がどこまで同じ業務内容にチェックを入れられるかを比べます。費用はかかりません。

### 7-7　判定と店の選択が違ったとき（私の案）

HPの判定にない業務内容に店がチェックを入れたとき（例：判定は「仲介」だけ、店が「相続・税」を足した）、そのずれは情報です。その業務内容の横に一行出します。
> 重視は「相続・税」ですが、HPからは相続の案内が見つかりませんでした。HPに載せると、訪問者にも伝わります。

責める文にはしません。HPをどう直すと効くかの入口になり、HP制作の営業材料になります。

### 7-8　営業での使い道

営業先のURLを入れるだけで、その店のタイプ1ができます（11-07・11-09 のアイデア）。API を使わないので、何社分作っても費用がかかりません。

## 8. 書き欄と「この中にない」

書き欄は置きません（Claude Code の案3に賛成）。足したいのは一点です。

**どの段にも「この中にない」を必ず置きます。** 押すと問い合わせの欄が開き、言葉はそこに書けます。押された場所は記録し、全体図に「ここで『この中にない』が◯回」と出します。

- 客には、行き止まりがなくなります。
- 店には、次に足す枝の場所が分かります。
- 売る側には、「言葉を受けたくなったら2・3へ」という上がり道になります。

## 9. 終わり方 ― セッションの完結を促す（ユーザー、11-16）

**決まり（ユーザー）：最後から2回目の選択から、選択肢に「詳しくはメールで問い合わせる」を入れる。最後は「セッション情報をもとにメール問い合わせを行う」で、セッションの完結を促す。**

これを、深さが枝ごとに違うタイプ1に当てはめます。

| 場面 | 画面 |
|---|---|
| 残りが2段以下になった段 | ふつうの選択肢の最後に［詳しくはメールで問い合わせる］を足す |
| 最後の段の返事のあと | 選択肢は出さず、［セッション情報をもとにメール問い合わせを行う］だけを出す |
| 枝が1段しかないカテゴリー | 最初の段から［詳しくはメールで問い合わせる］が出る |

- 「残りが何段か」は、店の設定からプログラムが数えます。店は＋で段を足すだけで、ボタンを出す場所を決める必要はありません。
- ［詳しくはメールで問い合わせる］を押すと、残りの段を飛ばして、最後と同じ問い合わせの欄へ行きます。
- 最後の返事は、足りないものではなく、言い切ったものを理由にします。
  > ここまでの見立て（◯◯のあたり、約1,850万円が目安、角地で数％高く見た）が実際に合っているか、担当が確かめます。
- 問い合わせのボタンにも、4章と同じく中身を載せます。ボタンの下に「ピンの場所・土地の様子・選んだ道（◯項目）を添えます」と一行出し、何が送られるかを押す前に見せます。
- 問い合わせには、通った道（番号）とデータシートが添います。道がすべて選択なので、店に届くデータシートは3種の中でいちばん整います。
- 下に常設の問い合わせ（今の「これらの情報をもとにお問い合わせ」）は残します。選択肢の中のボタンは、終わりが近いことを知らせる役目です。

**問い合わせへの出口は二つになり、店に届く意味が違います。**

| 出口 | 客の状態 | 店への印 |
|---|---|---|
| ［詳しくはメールで問い合わせる］ | 道筋に乗って、先を聞きたい | 道筋が合っていた |
| ［この中にない］（8章） | 選べるものがなかった | ここに枝が足りない |

二つを分けて記録すると、店は全体図で、効いている枝と足りない枝を見分けられます。

## 10. 誰が買うか、値段と中身の差

| | 買う店 | 月々 | 強み | 弱み |
|---|---|---|---|---|
| 1 | 契約を増やしたくない店、言葉がぶれるのを嫌う店。HPが薄くても成り立つ | なし | 店の言葉がそのまま出る。データシートが整う | 用意していない話は受けられない |
| 2 | 客の肉声が聞きたい店 | API実費 | 客の言葉を追う | 返事はAIの言葉 |
| 3 | 道筋へ導きたい店 | API実費 | 誘導と言葉の両方 | 設定とHPの中身に左右される |

差は「AIの有無」ではなく「何を任せるか」で説明します。1は道筋を店が持ち、2・3は言葉をAIに任せます。「この中にない」の記録が貯まった店が、2・3へ上がります。

## 11. サンプルHP「AIボット不動産」での見せ方

**入口にタイプ1を置く案です。**

- メールを一斉に送っても、開いた人ごとのAPI費用がかかりません。
- 11-14 の課題（ボットは店のHPを材料に話すので、ボット自体の解説ができない）が解けます。サンプルHPに限り、選択肢に「このボットの仕組みを見る」を置けます。用意した文なので、解説を正確に言えます。
- 2・3は、その先の「AIと話してみる」として置きます。サンプルHP企画書10章の未決（3の区画に置くのは2か3か）は、「1を入口、2・3は選んで試す」で一つの答えになります。

## 12. 今の作りへの当てはめ（Claude Code へ）

| 使うもの | 足すもの |
|---|---|
| 地図・ピン・設問・公開データの表（`survey.js` ほか） | カテゴリーと条件札を決める関数 |
| `survey.js` の facts（条件札ごとの一文の元） | 選択肢・文・条件・特例の入れ物（木ではなく、段ごとの一覧） |
| 単純計算の目安、`altland.js` の査定と候補 | 選択肢に数字を載せる表示、データの穴の差し込み |
| HPの読み取りのうちプログラムの分（`shop/read.js`・`listings.js`） | 業務内容を判定する決まり（7-6）。業務内容ごとの初期設定の一式。扱う地区との照合 |
| `?ai=off` の台本の経路 | これをタイプ1の本線にする |
| 記録・利用状況・問い合わせ欄 | 「この中にない」の記録と全体図 |

**最初の一歩の案。** カテゴリー4つ × ④の選択肢（数字つき・理由つき）× 返事1段 → 問い合わせ。ここまでで「選ぶたびに一つ知る」が成り立つかを、ユーザーのテストで確かめます。＋ボタンと全体図はその後です。
