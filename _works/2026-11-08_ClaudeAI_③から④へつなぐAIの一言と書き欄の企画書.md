# 選択の前にある AI の一言と、③以降の「選択＋書き欄＋送信」— 試して触るための企画書

筆者：Claude.AI ／ 読み手：Claude Code
材料：11-07 のテスト（セッション a8821a94、13:38〜13:41）。ユーザーから受け取った PDF・API の記録（log-2026-11-07.jsonl の 5〜8行目）と、`docs/proto/index.html`・`admin_mode.html`・`server/system.txt` の現状。
（11-08 改訂：対象を③→④だけでなく、**選択が入る段階すべて**に広げた。ユーザーの指摘による）

## 0. 目的

ユーザーの要望は「実際にやってみて、触ってどうかを試したい」。ここに書くのは決定事項ではなく、**触れる形にするための依頼**。作り方の細部は Claude Code の判断に任せる。

今の到達点は、「店がどんなサービスをもくろむか知らないまま、それなりの会話が進む」ところまで（ユーザーの認識）。次は、**業態モードの初期値だけで、店らしい流れが生まれるか**を試す段階。

考え方の芯：**次に選択（ボタン）が出る段階では、その前の AI の一言が、お客さんの答えを受け止めて、次のボタンへつなぐ役を持つ**。③→④、④→⑤、⑤→⑥、⊕で足した段階も同じ。選択が入るものすべてが対象。

## 1. テストで分かったこと（依頼の根拠）

- **③→④の一言は台本で、お客さんの答えを読んでいない。** 「住んでいるなら、建て直しは先の話です」と出たが、お客さんは④で「住む・建て直す／できれば建て直したい」と答えた。続く「〜などについてお話ししましょう」はボタンの読み上げで、受け身。④→⑤も、AI が空の返事だったため台本の読み上げになった。
- **AI に店の構えが渡っていない。** 記録の context にあるのは、条件・事情の積み重ね・相談の方向・次のボタンだけ。モード名（「土地の活かし方から一緒に考える店」）も各段階の問いの軸も渡っていない。
- **本音が最後の往復で出て、受け止められなかった。** ⑦で「土地の売却も視野」と書かれたが、最後の往復の指示が「直前への答えだけ、新しい話題は出さない、問いもない」だったため、AI は踏み込めなかった。締めの定型文（「接道の条件で…」）は建て直しの枝のまま。⑧のお問い合わせ欄には「売却を視野、早い妥結を希望」と書かれていた。
- ④の返事が空だったのは max_tokens（600）切れ。11-07 に 2000 へ直し済み。

## 2. 依頼A：③以降はすべて「ボタン（任意）＋書き欄（任意）＋送信」

- ③から先の各段階（⊕で足した段階を含む）を、④と同じ形にそろえる。**ボタンを押しても送らない**（選んだ状態になるだけ。押し直しで外せる）。送るのは「送信」ボタン。
- ボタンだけ、書き欄だけ、両方、のどれでも送れる。どちらも空なら送信は押せない。
- ①②は今のまま（ボタンを押したらすぐ進む）。
- 書き欄の薄い文字（プレースホルダー）は、業態モードの受け方に沿った例にする。例（総合系の③）：「ほかに気になることがあれば一言どうぞ（例：売ることも少し考えている）」。設定画面で店が変えられるとよい。

ねらい：今回の事例なら、③で「住んでいる家がある＋売ることも考えている」と一言足せた。⑦でやっと出た本音が、③で出せる。

## 3. 依頼B：選択が入る段階の前の一言を、すべて API で作る

対象は、次にボタンが出るすべての段階の前の一言。

| 段階 | 今 | 依頼 |
|---|---|---|
| ③→④ | 台本（`onIntent()` の3種類の文＋ボタンの読み上げ） | API で作る。台本はつながらないときの代わりに残す |
| ④→⑤ | API（失敗時は台本の読み上げ） | 渡すものを足す（下記）。⑤は枝でボタンが変わるので、枝が決まってから一言を作る（依頼E） |
| ⑤→⑥、⊕で足した段階 | API | 渡すものを足す（下記） |

**どの段階でも渡すもの**
- 場所（都道府県・市区町村・ピンの住所付近）、面積、公開データ（なければ「なし」）
- ここまでの答え（各段階で、選んだボタンと書いた言葉の両方）
- 業態モードのモード名と受け方（依頼C）
- **次の段階の問いの軸**（④なら topic、⑤なら枝の名前、⑥以降・⊕の段階はその topic）と、**次のボタン一覧**

**AI への指示（文面は調整してよい）**
- ここまでの答えを受け止めて、この土地・この相談の見立てを一言で返す。
- 受け方と次の問いの軸に沿って、次のボタンのどれかで答えられる問いで終える。ボタン名を並べて読み上げない。
- 150字程度。
- 次のボタンがない段階（店のボタンが尽きた後）は、今の決まり（書いて答えやすい短い問い）のまま。

**扱い**
- ③→④の一言は、AI の最初の発言として会話の履歴（AI_HIST）に入れる。④以降がこの見立てを踏まえて続くようにするため。
- 設計メモの「渡したもの／開けた穴」も、AI の返事のときの書き方に合わせる。

**今回の事例で期待する③→④の返事（総合系の場合の一例）**

> 住まいのある120㎡で、前の道が狭いなら、建て直すと敷地が少し削られるかもしれません。だからこそ弊社は、建て直す・貸す・売るを同じ表に並べてから決めることをお勧めしています。いま一番気になっているのはどれですか？

## 4. 依頼C：業態モードの初期値に「受け方」を足し、AI に渡す

`admin_mode.html` の `MODES` は、モード名・④の問いの軸・ボタン・締めを持っているが、**お客さんの答えをその店がどう受け止めるか**がない。各モードに一文を足す。設定画面で店が書き換えられる欄にする。「一から自分で作る店」は空（空なら AI には渡さず、今の会話のまま）。受け方はモードに一つで、③→④だけでなく、選択が入るすべての段階の一言に使う。

| モード | 受け方（初期値の案） |
|---|---|
| m1 物件情報をいち早く届ける店 | お客さんの答えを、買い手がまず見る点として受け止める |
| m2 土地を買い取り、形にする店 | お客さんの答えを、この土地に何が建つかの条件として受け止める |
| m3 土地の活かし方から一緒に考える店 | お客さんの答えを、選べる活かし方の幅として受け止め、一つを勧める前に並べて比べる |
| m4 相続や税の相談から始める店 | お客さんの答えを、この土地を誰がどう持つかの話として受け止める |

ねらい：手書きの「店の構え」を用意しなくても、モードを選ぶだけで店らしい流れになるかを試す。後で HP の URL から店の構えを読み取る機能を作るときも、この受け方の欄を店の言葉で上書きする形になる。

## 5. 依頼D：プロンプトの決まりを足す（`server/system.txt`）

- **ボタンと書いた言葉が食い違ったら、書いた言葉を優先する。** 今は「後から答えた内容に沿って」しかなく、同時に来た場合の決まりがない。
- **答えの代わりに質問を返されたら、先に短く答えてから流れに戻る。**
- 冒頭の「岐阜市などの自分の土地」の地域の決め打ちを外す（東京都中央区のテストで不自然）。

## 6. 依頼E：枝の判断と、⑤の前の一言を同じ往復で

- 今は④でボタンを選ばずに書いた場合、枝は**ダミーで枝1に固定**（`index.html` のコメント「書いた場合の枝はAIが判断（ダミーは枝1）」）。AI に枝を判断させる。
- ⑤のボタンは枝で変わるので、**枝の判断と④→⑤の一言は同じ往復で作る**のが筋。返事とは別に枝の番号を返させ、その枝のボタンへつなぐ一言を返させる、など。方法は任せる。
- 食い違い（ボタンは枝1、書いた言葉は枝2寄り）のときも、書いた言葉を優先して AI が判断する。

## 7. 記録

- 「ボタンを選ばずに書いた」「ボタンと書いた言葉の両方」が、開発の利用状況で見分けられるようにする（meta の press と typed で分かるなら、表示だけでよい）。ボタンに収まらなかった聞き方は、店がボタンを直す手がかりになる。

## 8. 試すときに見ること

- a8821a94 と同じ入力（東京都中央区・120㎡・道に広く面している・すれ違えない・住んでいる家がある）で、③→④、④→⑤の一言がどう変わるか。総合系と相続・税で、同じ事実への一言が変わるか。
- ③で「売ることも考えている」と書き足したとき、以降の一言がそれを受け止めるか。④で書き欄だけで送ったとき、枝と⑤の一言がかみ合うか。
- ⊕で段階を足したとき、その段階の前の一言が、足したボタンへつながるか。
- **ユーザーが挙げている課題**：自由に書けるようになると、ひな形のボタンが、書いた言葉から見て矛盾した選択肢に見えることがある（例：③で売却を書いたのに、⑤が「自分で活かす」の枝のボタン）。今回は解かずに、**触ってどう見えるかを確かめる**。気づいた場面は記録しておく。
- 費用：③→④の分で1セッションに1往復増える（11-07 の記録の単価で約 0.015 ドル）。
