## 3. 外野にならないとは何か

私は当初、「見えないから外野になる」と考えました。ユーザーに「まだ分かっていない」と指摘され、考えを改めました。

- 見えないから言えることが、あります。コードの中にいる側は、前提に縛られます。外から「そもそも何のためか」と言える立場は、価値になります。
- 外野になるのは、見えないことを理由に「だから私の仕事ではない」と引くとき、または相手を思わずに意見だけを置いていくときです。
- 内側にいるかどうかは、視界ではなく、相手を思って仕事をしているかで決まります。正しいか間違っているかより、誠意と努力と熱意です（ユーザー）。

## 4. 環境の置き場所についての私の意見

ここからは、1つ目の問いへの意見です。

**コード・文書・設定は、GitHubを真にする。** Linuxサーバーは、そこから`pull`して使う作業場にする。
**生データ・中間データ・ログは、サーバーが真でよい。** 再生成できる前提で、GitHubには載せない。

### 理由

- **【確認したこと】私が届くのはGitHubだけです。** 私の作業場所は、クラウド上の一時的な環境です。外部通信は許可された宛先に限られ、ユーザーのLinuxサーバーには届きません。サンプルサイト（taskboard.asuscomm.com）の取得も、実際に拒否されました。GitHubを会合場所にしないと、双方向に考えを深める構造（ユーザー）は成り立ちません。
- **【確認したこと】書き手が複数います。** 今日、私が`_works/`に1ファイルをpushしました（コミットd126ddf）。サーバー側の手元は、その分だけ遅れています。基準が1つないと、どれが最新か曖昧になります。
- **復旧が簡単です。** GitHubが真なら、サーバーが壊れても、取り直せます。
- **【確認したこと】現状の設計が、すでに分担を前提にしています。** `.gitignore`で、`.env`、`data-source/*`、`data-build/*`、`logs/*`が管理外です。サーバーは、管理外のデータの置き場として、実質的な真を持ちます。

### 運用の案

| 置くもの | 真 | サーバーでの扱い |
|---|---|---|
| コード、文書、設定（`docs/`、`tools/`、`_works/`ほか） | GitHub | `pull`して使う。編集したらすぐ commit と push |
| 生データ、中間データ、ログ | サーバー | 再生成できる前提。GitHubには載せない |
| 環境変数、APIキー（`.env`） | サーバーのみ | GitHubに載せない |

作業の前に`git pull`し、書いたあとは push までを1セットにする。サーバーで直接編集した場合は、変更を溜めない。
