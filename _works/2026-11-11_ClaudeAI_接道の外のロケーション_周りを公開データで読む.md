## 0. この書面が生まれた経緯

- ユーザーは前から、「ロケーション」の評価が接道中心でよいのかを気にしていた。
- 11-10 に地図の作りを上げてもらった（航空写真・ストリートビュー・レシート）のも、**ピンの位置は確かだ**という前提を固めるためだった。位置が確かなら、接道の外のロケーションも評価に入れられる。
- ユーザーの見方
  - 接道は安全（建て直せるか）を考えてもらうための問いだが、相談の大多数は住宅地のニーズ。住宅地なら、**公共物・駅などは土地評価の重要な視点**。
  - 工業地なら高速道路などが加わる程度でよい。「近くにショッピングセンターがあるから工場に向かない」といった話は、そこまで気にしなくてよい。
  - 近隣施設の読み取りは、無料のAPIか、工夫の範囲に限る。

### Claude.ai の考え（ユーザーの方向に、一歩足したもの）

1. **「敷地」と「周り」を分ける。**
   - 敷地（接道・形・段差・境界）は、持ち主の目でしか分からない。だから設問で聞く（いまの①〜③のまま）。
   - 周り（駅・学校・災害・人口の先行き）は、ピンが確かなら公開データで読める。**だから客に聞かず、システムが読んで見せる。**
   いまの「ロケーション」は、実は敷地の話だけでした。周りを足して、ようやく名前どおりになります。
2. **何を重く見るかは、ピンの用途地域で自動で切り替える。** ユーザーの「住宅地なら駅・公共物、工業地なら高速道路」という見方を、そのまま仕組みにします。用途地域はすでにピンで取れています（XKT002）。店の設定はいりません。
3. **新しいAPIはいらない。** いま使っている国土交通省「不動産情報ライブラリ」（無料・同じキー・同じタイル取得の仕組み）に、必要なものがほぼそろっています。

## 3. 段階1で入れるもの（住宅地のニーズに効くものから）

1. **駅**：最寄り駅2つまで。駅名、路線、直線距離、乗降客数。
2. **学校区**：ピンが入る小学校区・中学校区の名前と、その学校までの直線距離。
   住宅地の買い手には、学校までの距離より「どの学区か」が効きます。
3. **災害**：洪水・高潮・津波・土砂のうち、ピンが入るもの（浸水の深さのランクなど）。入っていなければ「指定なし」。
4. **人口の先行き**：ピンのメッシュの将来推計人口（今と比べて増えるか減るか）。
5. **居住誘導区域**：ピンが居住誘導区域の内か外か（立地適正化計画がある市だけ）。

段階2：医療・保育・役場・図書館、IC（ファイルを県単位で取り込む）、商業施設（OpenStreetMap の Overpass。無料だが、使い方の決まりと日本での登録の粗さがあるので、入れるかは段階1を見てから決めます）。

## 4. 見せ方と言い方の決まり

- **距離は「直線で約〇m」と書く。「徒歩〇分」とは書かない。** 不動産の広告の徒歩分数は、道路距離80mを1分とする決まりがあります。直線距離から分数を出すと、実際より近く見えます。「駅近」とも言いません。
- **地図のレシートに印を出す**（駅・学校・ピンが入る区域の色）。「何を見て答えたか」を見せる、11-10 の考え方の続きです。
- **データシートの見出しを分ける**：「土地の様子（お答えより）」と「周り（公開データ）」。
- **災害は隠さず、あおらない。** 浸水などの想定は、売買の重要事項説明でも伝える事項です。客優先なら、先に知らせる価値があります。AIは事実を一言で伝え、「現地と対策を担当が確かめます」につなげます。いまの「不安を強める言い方はしない」は、そのまま守ります。
- **人口の先行きと居住誘導区域は、値段の話にしない。** 「売る・貸す・残すを考える時期の手がかり」として扱い、値上がり・値下がりの予想はしません。
- 出典の一文は、いまの SOURCE_NOTE のままで足ります（国土数値情報も、このAPIの提供情報として出ます）。

## 5. AIへ渡すもの

データシート全体ではなく、**レンズを通した要約を数行**だけ渡します（話がデータの読み上げにならないように）。

```
【周り（公開データ・直線距離）】レンズ：住居系
・駅：〇〇駅（〇〇線）直線約850m、乗降客数 約1.2万人/日 ／ △△駅 直線約1.4km
・学区：〇〇小学校区（学校まで直線約400m）、〇〇中学校区
・災害：洪水の想定区域（0.5〜3m）に入る。土砂・津波は指定なし
・人口の先行き：このあたりは2040年に今より約2割少ない推計
・居住誘導区域：内
```

AIへの決まり（`system.txt`・`system_talk*.txt` に足す）：
- 周りのことは、利用者の話と重なるときに一つだけ触れる。読み上げない。
- 11-11 の書面A（利用者の言葉 × 公開データ × HPの強み）の「公開データ」に、ここが入ります。例：居住誘導区域の外で人口が減る推計＋相続した空き家 → 「残すか売るかを早めに考える手がかりになります」。
- 直線距離を徒歩分数に言い換えない。

### 5-2. Claude API に「座標の近くに何があるか」を聞かない

ユーザーの問い（11-11）：国交省のデータを取るのと同じタイミングで、Claude API に「この座標の近くに何がある？」と聞く手もあるのでは。

Claude.ai の考え：**施設を探す役は、Claude API にさせない。**
- AIは座標から周りの施設を「知って」いるわけではありません。それらしい店名や距離を作ってしまう恐れがあります。不動産では、周りの施設の表示の正確さに決まりがあり、一つの作り話が店の信用を落とします。
- いまの「書かれていない数字は言わない」という決まりとも合いません。

Claude API の使いどころは、次の2つです。
1. **探すのは公開データ、意味づけはAI。** 同じタイミングで、5章の要約（事実）をAIに渡し、レンズに沿った「周りの見立て」の一言にします。数字は渡したものだけを使います。会話の中でいまやっていることを、ピンの直後にも一度やる形です。
2. **地域の材料は、店ごとに一度だけ集める（段階2の候補）。** 11-03 に手で集めた「鷺山の地域材料」のような、町の性格や暮らしの話です。Claude API の Web検索で出どころ付きで集め、店が管理画面で確かめてから使います。HPの「読み取る」ボタンと同じく、押したときだけ走らせます。ピンごとには走らせません。

## 7. Claude Code へのお願い

1. 段階1の実装（3章）。
2. 1ピンあたりの呼び出し数と待ち時間の見込み。タイルの保存が効けば2回目からは速いはずですが、初回の待ちが長いなら、公開データの表を先に出し、周りは後から足す形でかまいません。
3. 各APIの対応ズームと、駅・学校の「最寄り」を探すときに何タイル読むか。
4. 立地適正化計画がない市、学区データがない所での出し方（「データなし」を利用者の不安材料にしない、いまの決まりに合わせる）。
5. 段階2の IC と商業施設について、無料でやれる範囲の見立て。
