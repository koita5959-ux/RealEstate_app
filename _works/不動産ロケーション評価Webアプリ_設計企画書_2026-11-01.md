# 不動産ロケーション評価Webアプリ 設計企画書

## 1. 企画目的

不動産サイト本体へ組み込む前段として、独立したHTML Webアプリを試作する。

利用者が都道府県・市区町村を選択し、地図上で任意地点をクリックすると、その地点に対応する不動産関連の公開データ・自前整備データを検索し、参考情報・数値・周辺特性を表示する。

本アプリの目的は「不動産価格を自動査定すること」ではない。

最初の目的は、

**地点を指定する → その地点について取得できる情報を集約する → 判断材料として見せる**

という基盤を作ることにある。

将来的には既存の不動産サンプルサイトへ組み込み、

- 土地そのもの
- 周辺環境
- 都市計画
- 市場価格
- 災害リスク
- 将来人口
- 利用可能性
- 売却・保有・活用等の出口

を一つのロケーションから横断的に考える仕組みへ発展させる。

---

## 2. 基本方針

### 2-1. 基本Free構成

原則として有料地図API・有料不動産データベースを使用しない。

初期構成候補：

- HTML
- CSS
- JavaScript
- Leaflet
- OpenStreetMap
- GeoJSON
- JSON
- CSV
- 国・自治体等の公開データ

Google Maps API等を前提としない。

ただしOpenStreetMap標準タイルについても無制限の商用配信サービスではないため、公開規模が大きくなった段階ではタイル提供方法を再検討する。

## 3. ユーザー操作

基本フローは以下。

```text
都道府県を選択
    ↓
市区町村を選択
    ↓
対象地域の地図を表示
    ↓
地図上で任意地点をクリック
    ↓
マーカー表示
    ↓
「この場所を調べる」
    ↓
地点情報を検索
    ↓
結果表示
```

住所入力を必須にはしない。

理由：

- 空き地
- 山林
- 農地
- 大きな土地
- 住居表示のない場所
- 分筆予定地
- 住所を知らない土地

にも対応できるため。

内部では最終的に、

```json
{
  "lat": 35.423,
  "lng": 136.760
}
```

のような緯度・経度を地点識別の基本値として使用する。

## 5. 最重要設計

本システムを、

**「地図Webアプリ」**

と

**「不動産データライブラリー生成システム」**

に分離する。

ここを強く意識する。

```text
公開データ
   ↓
データ取得
   ↓
変換
   ↓
正規化
   ↓
検証
   ↓
アプリ用ライブラリー生成
   ↓
────────────────
   ↓
Webアプリ
   ↓
地点検索
   ↓
結果表示
```

Webアプリから各行政サイトへ毎回問い合わせる設計を基本にしない。

可能なデータについては事前に取得・整形し、

```text
/data
```

以下へアプリ専用ライブラリーとして保存する。

## 6. ライブラリーデータ生成システム

別途、

```text
/tools
```

を設ける。

これは公開Webアプリではなく、管理者がデータ更新時に実行する仕組みとする。

例：

```text
/tools
    build-data.js
    import-mlit.js
    import-municipality.js
    normalize.js
    validate.js
```

またはPythonであれば、

```text
/tools
    build_data.py
    import_mlit.py
    normalize.py
    validate.py
```

どちらでも構わない。

Codex / ClaudeCode側で保守性を考えて選択すること。

## 7. データ作成処理

基本処理：

```text
SOURCE
↓
DOWNLOAD
↓
RAW保存
↓
PARSE
↓
NORMALIZE
↓
GIS変換
↓
INDEX生成
↓
VALIDATE
↓
RELEASE
```

### RAWデータ

元データは改変せず保持する。

```text
/data-source/
    mlit/
    nta/
    municipality/
```

### 変換済み

```text
/data-build/
```

### Web公開用

```text
/public/data/
```

とする。

---

## 8. データの3層管理

最低でも次の3層に分離する。

### Layer 1：Source

取得した原本。

```json
{
  "source": "MLIT",
  "retrieved": "2026-11-01",
  "original_file": "xxxxx.geojson"
}
```

### Layer 2：Normalized

アプリ内部で共通利用できる形式。

### Layer 3：Published

Webブラウザーから高速検索するために最適化したデータ。

これにより、元データ形式が変更されてもWebアプリ本体を変更せずに済む構造を目指す。

---

## 9. データ共通スキーマ

すべての情報に最低限以下を持たせる。

```json
{
  "id": "landprice_21201_001",
  "type": "land_price",
  "geometry": {
    "type": "Point",
    "coordinates": [
      136.760000,
      35.423000
    ]
  },
  "properties": {
    "prefecture": "岐阜県",
    "municipality": "岐阜市",
    "value": 78000,
    "unit": "JPY/m2",
    "year": 2026
  },
  "source": {
    "organization": "国土交通省",
    "dataset": "地価公示",
    "retrieved_at": "2026-11-01"
  }
}
```

出典情報をデータそのものへ保持する。

## 11. 最初のMVPデータ

初回実装では次の5系統程度に限定する。

### A. 地価公示・地価調査

選択地点の近傍にある標準地を検索。

表示：

```text
最寄標準地
距離
価格 / ㎡
調査年
```

### B. 不動産取引価格

一定距離内の実取引を抽出。

例：

```text
半径500m
半径1km
```

土地種別等で可能な範囲のフィルターを行う。

単純平均だけではなく、

```text
件数
中央値
最低
最高
```

を保持すること。

### C. 用途地域

地点がどのポリゴンに含まれるかをPoint-in-Polygonで判定。

```text
用途地域
建ぺい率
容積率
```

等を表示可能にする。

### D. 周辺施設

最初は、

- 駅
- 小学校
- 中学校
- 医療機関

程度。

地点から各施設までの直線距離を計算する。

### E. 防災

1〜2種類から始める。

例えば、

- 洪水
- 土砂災害

地点が対象GISポリゴン内に含まれるかを判定する。

## 12. 路線価について

路線価は初期MVPの必須要件にはしない。

国税庁では最新年度を含む路線価図・評価倍率表を公開している。路線価は1㎡当たり千円単位で表示される。

ただし、国土交通省の不動産情報ライブラリAPIのように、地点座標から容易に取得できる公開APIとして今回確認できたものではない。

そのため、

```text
路線価を無理に初回から自動取得しない
```

こと。

将来、

```text
NTAImporter
```

のような独立モジュールとして追加する。

データ取得方法・利用条件・地図座標との対応方法を確認した上で実装する。

Webアプリ本体へ国税庁HTML/PDF依存コードを書かない。

---

## 13. 地理検索エンジン

ユーザーが地点Pを指定した場合、各データを同じ方法で検索しない。

3種類に分ける。

### Pointデータ

例：

- 標準地
- 学校
- 駅
- 病院

地点Pからの距離を計算する。

```text
nearest()
withinRadius()
```

### Polygonデータ

例：

- 用途地域
- 洪水区域
- 土砂災害区域

```text
contains(point)
```

によって判定。

### Lineデータ

将来的な路線価や道路等。

```text
nearestLine()
distanceToLine()
```

を使う。

この3分類を最初からコード上で分離しておく。

例：

## 18. validation

データ作成時に最低限以下を検査。

```text
緯度が存在する
経度が存在する
日本国内座標である
市区町村コードが存在する
重複IDがない
数値形式が正しい
年度が存在する
出典が存在する
```

GISについては、

```text
Geometryが有効
Polygonが閉じている
座標系が統一されている
```

ことも確認。

不正データは公開用ライブラリーへ混入させずログへ出す。

**「査定」ではなく「周辺データ」**

として表示する。

## 26. Codex / ClaudeCodeへの実装要求

今回重要なのは、単に動く地図サンプルを作ることではない。

次の構造を守ること。

```text
UI
≠
MAP
≠
Geo Query
≠
Data Library
≠
Data Builder
```

各責務を分離する。

特に、

**外部公開データ → アプリ専用ライブラリー**

への変換工程を正式な機能として設計すること。

データ更新時にWebアプリのコードを書き換える構造にしてはいけない。

---

## 27. 今回の設計思想

このWebアプリの価値は、

「地図をクリックすると価格が出る」

ことだけではない。

一つの地点を基準に、

```text
価格
+
周辺
+
都市計画
+
災害
+
人口
+
利用可能性
```

を同じ位置情報から引き出せることにある。

最終的には、

**「この土地はいくらか」ではなく、「この場所をどう見るか」**

を支援するアプリへ発展させる。

これは現在制作している不動産サイトの、

「土地だけを見ても、その不動産を十分に評価できない」

という考え方をWebアプリへ変換する基盤として位置付ける。
