# URLから店を判断するプログラム ── 設計書
――Claude.AI　2026-11-09

Claude Code へ。

AI型の初期ボタンを Claude.AI が考案したのと同じ位置づけで、今回は「管理画面にURLを入れると、その店の誘導テンプレができるまでの判断の流れ」を考案しました。土台はユーザーとの打ち合わせ（11-09、対話型の企画）です。（ユーザー）はユーザー本人の考えです。

## 0. 決まったこと（打ち合わせより）

- 管理画面で店が入れるのは **URL**。そこから先はシステムが判断する（ユーザー）。
- 対話型（タイプ2）の骨組みは AI型と同じ。⓪〜③共通、④⑤と⊕も同じ。往復の上限の考え方も同じ（ユーザー）。違いは、段にボタンを渡すかどうか（Claude Code「材料」11-09 の見立てどおり）。
- AIボットの革新は **「考慮はするが独自判断をする」**（ユーザー）。HP・指定URL・国の記録・ページ名・客の言葉は、どれも考慮する材料で、どれも真に置かない。
- Google の API は使わない（ユーザー）。理由：AI検索の時代に Google から引く情報は、Google のAIが選んだ結果で、それを材料にすればそのおすすめをなぞるだけになる。
- 公開時のURLの初期値は見本サイト自身。URLを変えると「見本の上で、別の店のボットとして話す」状態になる。AIトークをもとにHPを直すことも視野にある（ユーザー）。
- ページ名や検索向けの説明文はヒントになるが、口コミ探しはその視点ではない（ユーザー）。

## 1. 出口：今の管理画面の形そのものを作る

`docs/proto/admin_mode.html` の `MODES` の1件と同じ形を出力する。

```
{ name, sub,
  stance,                       // 受け方
  hint,                         // 書き欄の例
  s4: { topic, btns:[[文言, 枝]] },
  s5: [ {name, kind:"答える"|"聞く", btns, close} ×2 ],
  close }                       // 問い合わせに添える一文
```

- AI型ならボタンまで、対話型なら `btns` を空にして題（topic・枝の name）だけを使う。**一つの生成で両方に使える。**
- 店は生成された設定を管理画面で見て、直せる。生成は初期値づくりで、店の判断を置き換えない。

## 2. 判断の流れ（5段）

意味を読むのはAI、数えて拾うのはプログラム（11-04 の分け方）。APIを呼ぶのは B・C・D の3回で、URLの登録時に1回だけ走らせて結果を保存する（会話のたびには走らせない）。

### A　読む（プログラム、APIなし）

- サーバーがURLを直接取りに行く（検索エンジンを通さない）。
- 取るもの：トップページの `<title>`、説明文（meta description）、ページ下の著作権表記、本文テキスト（長さに上限）、リンク一覧。
- リンク一覧から「会社概要・会社案内・事務所概要・アクセス・プロフィール」に当たるページを **一段だけ** たどって、同じものを取る。
- 決まった形のものはプログラムが拾う：
  - 宅建の免許番号（例：「愛知県知事(3)第12345号」「国土交通大臣(2)第…号」）
  - 電話番号、郵便番号つきの住所
- 転送（リダイレクト）は追う。取れなかったページは「取れなかった」と記録して先へ進む。

### B　身元（API 1回）

Aで集めた材料を渡し、次の形で返させる。

```
{ 屋号, 商号, 免許番号, 所在地, 電話,
  運営の形: "店自身" | "運営会社の窓口サイト" | "士業" | "団体・ポータル",
  読めなかった項目: [...] }
```

指示の芯：
- **書かれていないものは作らない。** 見つからなければ「不明」。名前を推して作文しない。
- ページ名と著作権表記が食い違えば、屋号と商号の両方を残す（ページ名には屋号、著作権表記には商号が出やすい）。
- HPの持ち主と相談を受ける店が別のこともある（例：41件の #3 は相談窓口のサイトで、運営は別会社）。

### C　店の中身（API 1回）

本文を渡し、店が **実際に何をしている店か** を読ませる。

```
{ 手段: 売却の仲介 / 買取 / 開発・建売 / 活用・賃貸 / 相続の窓口 …（複数可）,
  受ける事情: 空き家 / 相続 / 住み替え / 収益物件 …,
  姿勢: "話を聞いてから動く" | "査定・買取から入る",
  近い型: 4＋1のどれか と 二番目,
  根拠: [HPのどの記述からそう読んだか（短く）],
  宣伝文句: [選ばれるための言葉として除いたもの] }
```

指示の芯：
- **宣伝文句（検索向けの言葉）と中身を分ける。** 「AIが推奨する」「地域No.1」のような言葉は判断に使わない。サービスの説明、料金、流れ、実績の書き方から読む。
- 店名や見出しの言葉で型を決めない。店が客を **どこへ引き寄せたいか** で決める（Claude.AI がこの日、「仲介情報屋」という呼び名だけで売却の店を枠外と読み違えた。その癖への歯止め）。

### D　テンプレを作る（API 1回）

Cの結果と、近い型の初期値（今の `MODES`）を渡し、1の形で返させる。

- 近い型の初期値を土台に、**その店の中身に合わせて** 題・ボタン・枝・締めを書き換える。例：「売る前相談」を前に出す店なら、④を売る前の迷い（理由・時期・住まいの状態・家族の考え）に寄せる。
- 受け方（stance）は、店の姿勢から書く。
- 締めの文は、店が問い合わせで実際にしてくれること（HPに書いてあること）から書く。書いていないことを約束させない。
- 文の長さ・ボタンの字数は今の決まりに合わせる（ボタン7文字前後）。

### E　店に見せる（管理画面）

- 生成した設定を、いつもの管理画面に入れて見せる。
- 各所に **根拠**（HPのどこから作ったか）を小さく添える。
- **読めなかった項目** を一覧で見せる（免許番号が見つからない、など）。
- 店は直してよい。ただし身元（B）は店が書き換える欄にしない。外から見る視点に店の手が入るため。

## 4. 「わからなかった所」の記録（後でつなぐもの）

会話の中でAIが「それはHPからはわかりませんでした」と答えた所を記録しておくと、一つで三役になる（Claude.AI の意見、ユーザーとの打ち合わせで出たもの）。

1. 見本：見本サイトは自分を読むので、ここがほぼ空になるよう作る。それ自体が「読まれる前提のHP」の実演になる。
2. 試用：URLを変えた見込みの店では、これが作り直しの提案になる。
3. 導入後：客が聞いたのに答えられなかったことの一覧が、修正オーダーの中身になる。

あわせて **「伝わった所」** も記録する。客がHPのある記述に反応して話が進んだ所、問い合わせにつながった話題など。自分を評価できないのは店も同じで、足りない所だけを返すと、店は自分の強みを知らないまま終わる。「わからなかった所」は作り直しの提案に、「伝わった所」は店が自分の売りを言葉にする材料になる。URL判断の段階でも、Cで読み取った店の芯（例：試作の架け橋不動産では「すぐ買取／じっくり買取」の二本立て）は、最初の「伝わった所」として店に見せられる。

今回の設計には入れない。Eの「読めなかった項目」と同じ記録の仕組みに載せられるよう、置き場だけ揃えておいてください。

試作：`2026-11-09_ClaudeAI_試作_URL判断を1店で通す_架け橋不動産.md`（A〜Dを1店で通したもの）

## 5. 41件で試す

`2026-11-09_ClaudeAI_タイプ別サイトのサンプル41件.csv` を試験台にする。正解はない（ユーザー）。見るのは比べたときの差。

- **Aのカバー率**：41件のうち、身元が全部取れた／屋号だけ／読めなかった、の割合。「うちのURLで試してみよう」にどこまで応えられるかの数字になる。
- **Cの型**：ユーザーの札と、AIの「近い型」を並べる。食い違った所が、型の分け方を見直す材料になる。
- **Dの差**：同じ型と判断された店どうしで、題やボタンがどれだけ違うか。全部同じなら、HPを読む意味が出ていない。

41件は実在の店なので、試験の結果は内部にとどめ、見本サイトの上で人前に出さない。

## 6. タイプ2の制作の進め方とテストの立ち位置

### 役割（ユーザー）

| | 何をするか | 見る位置 |
|---|---|---|
| ユーザー | 試作コンテンツを入れる | — |
| Claude Code | プログラム〜入力値〜結果を見て判断する（いわゆるデバッグ） | 全容が見える作り手の位置 |
| Claude.AI | 結果をなぞり、改善点を探す | **全容が見えない客の位置** |

Claude Code と Claude.AI は同じ Claude で、能力や癖はほぼ同じ。違うのは立ち位置。

### Claude.AI の見る順番

1. **まず客として受ける。** ソースも設計の意図も見ずに、返ってきた返事だけで「相談する意味があるか」「次に何か言いたくなるか」を客の言葉で書き留める。
2. **そのあとで原因を探す。** 引っかかった所についてだけ、「送信と原文」やソースを見て、どこから来たかを確かめる。
3. **客の言葉で返す。** 改善点は「この一文で客は話す気をなくす」のように、客に起きることで伝える。

客は二人いる。土地の相談に来る訪問者（3類型：①土地持ち a/b、②投資家、③のぞき見する同業者）と、「うちのURLで試してみよう」と思う見込みの店。Claude.AI はどちらにもなって試す。

### Claude Code へ

- **思い切って試してください。** 試作の結果は、Claude.AI が客の位置で受け止めます。うまくいかなかった所は、客に何が起きたかとして返ってきます。ミスを先回りして避けるより、挑戦した試作の方が、客の目から見て得るものが多いはずです。
- この設計書の取り方や判断の順番は、Claude.AI が会話の側から考えた一案です。実物（41件）に当ててみて、もっとよい読み方・作り方が見えたら、そちらを取ってください。とくにAの「どう取るか」は、実物に触れられる Claude Code の方が確かです。
- Claude.AI 向けの説明やログの要約は要りません。Claude.AI は客と同じ入口（公開画面）から見に行きます。その分の力を、プログラムの挑戦に回してください。
- Claude.AI の指摘には、作り手の位置からの意見を持って返してください。二つの位置から見て、よりよいものを目指すのが、この協業の形です。
